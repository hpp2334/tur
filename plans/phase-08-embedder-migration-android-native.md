# Phase 8 — Embedder migration (`tur-android`, `tur-native`)

**Status:** not started
**Prerequisite:** Phase 7 (worker pool online on native).
**Goal:** migrate the native embedders from the old direct-call API to the new handle-based message API. Android auto-installs the Net plugin (no Handle plumbing). JNI trampolines updated for the new `TurApp` shape. `tur-native` (desktop entry point) likewise migrated.

## Background

After Phase 7 the engine's native path runs off-main-thread, but the embedders still:
- Construct `NativeHttp::new(handle)` with an explicit Handle.
- Call `push_platform_event` / `push_app_event` / `run_frame` / `set_after_frame_hook` directly.
- Use `with_app` for ad-hoc access (which was removed in Phase 5).
- Have JNI trampolines (`standard_jni_exports!`) tied to the old API.

Phase 8 makes them speak the new handle-based API.

## Changes per embedder

### `libs/tur-android`

#### `app.rs` — `AndroidRuntime::build`

```rust
// Today: NativeHttp::new(handle) explicit plumbing
let http = NativeHttp::new(tokio_handle.clone());
builder.capability(Http::new(http));

// Tomorrow: auto-install, no Handle arg
builder.plugin(TurNetPlugin);  // engine pulls Handle from runtime context
```

The runtime builder now requires `tokio_handle` (Phase 7). AndroidRuntime wires the embedder-supplied tokio runtime into the builder.

#### `lib.rs` — `standard_jni_exports!`

The macro generates trampolines for `createInstance`, `loadModule`, `pump`, `resize`, `pushPointer`, `pushKey`, `pushIme`, `focusedIsEditable`, `destroy`. Most of these map cleanly to `WorkerMsg` sends:

| JNI trampoline | Today | Tomorrow |
|---|---|---|
| `pushPointer` | `app.push_platform_event(PlatformEvent::Pointer(...))` | `app.worker_tx.send(WorkerMsg::PlatformEvent(...))` (via a helper) |
| `pushKey` | `app.push_platform_event(PlatformEvent::Key(...))` | same |
| `pushIme` | `app.push_platform_event(PlatformEvent::Ime(...))` | same |
| `resize` | `app.push_platform_event(PlatformEvent::Resize {...})` | same |
| `loadModule` (sync) | `app.load_module(src)` | `app.load_and_run_module(src.into()).await` — JNI must handle async (block_on or return a Promise-like) |
| `pump` | `app.run_frame()` | `app.pump()` — drains `main_rx`, processes MainMsgs, returns FrameOutcome |
| `focusedIsEditable` | `app.focused_is_editable()` | Reads cached `focused_state.is_editable` (no RPC) — same JNI signature |
| `destroy` | drops the instance handle | `app.worker_tx.send(WorkerMsg::Destroy { reply })` + await |

JNI is synchronous from Kotlin's perspective. For `loadModule`, the JNI trampoline must block on the async future (via `tokio::runtime::Runtime::block_on` on a current-thread runtime the embedder owns, or via `Handle::block_on`). Kotlin can't tell the difference.

#### `with_app` removal

`ops::with_app` (tur-android `lib.rs:534`) was removed in Phase 5. Embedder code that used it for `EventBus::of(&app)` switches to `app.event_bus()` directly.

For app-specific custom data flow, define a named handle type (e.g. `MyPlugin::handle(&self) -> MyHandle`) and expose it via a `TurApp` method — follow the EventBus pattern.

### `libs/tur-native`

The desktop entry point. Similar migration:
- Construct tokio runtime, pass Handle to TurRuntimeBuilder.
- rAF (or winit event loop) drives `app.pump()`.
- All event sourcing (winit input events) sends `WorkerMsg::PlatformEvent`.

### `demo/compose` — Kotlin side

- `TurRuntime` and `TurInstance` Kotlin wrappers updated for new builder signature.
- `nativePump(handle)` JNI signature unchanged; behavior internally uses `app.pump()`.
- `loadModule(handle, source)` becomes async — Kotlin exposes it as a suspend fn or returns a `CompletableDeferred`.

### `demo/compose/native` — `tur-demo` cdylib

- JNI trampolines generated by `standard_jni_exports!` (no manual changes — the macro abstracts them).
- Demo-specific `createEngine` function constructs the runtime with `tokio_handle` and the demo plugin set.

## Verification

1. **Android on-device test** — install the demo APK, verify rendering, input, scroll, text input, IME, clipboard.
2. **Desktop smoke test** — `tur-native` runs a simple app, renders, accepts input.
3. **Multi-instance** — demo can spawn multiple TurView instances on the same Android activity; verify isolation.
4. **No JNI thread-affinity violations** — verify the engine thread (worker) and the JNI thread (Choreographer) interact cleanly via the channels.
5. `cargo build --workspace` clean.
6. `cargo clippy --workspace -- -D warnings`.
7. `cargo test --workspace` — integration tests pass (they're embedder-agnostic).

## Risks

- **JNI synchronous semantics** — Kotlin expects `loadModule` to return when the module has executed. With async, the JNI trampoline must `block_on` the future. Need to verify this doesn't deadlock (the worker is on a different thread, so blocking the JNI thread is safe).
- **Choreographer thread vs engine thread** — today they're the same. After Phase 8, Choreographer (main) drives `pump`, engine work happens on a worker. The Kotlin `FrameLoop` fires `nativePump` on Choreographer ticks — same shape, but `pump` now does cross-thread work.
- **macOS `adb` Sequoia block** — pre-existing Android-dev concern (see `.opencode/skills/android-dev/SKILL.md` if it exists). Unrelated to Phase 8 but may slow device testing.
